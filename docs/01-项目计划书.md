# 口袋 CPM · 项目计划书

> 一个装在安卓手机里、断网也能看图聊天听话的离线多模态助手
>
> 版本 v0.1 ｜ 2026-10-25 ｜ 状态：待评审

---

## 1. 项目定位

| 项 | 内容 |
|---|---|
| 项目代号 | 口袋 CPM（Pocket CPM） |
| 一句话定义 | 全程离线的安卓多模态对话 App，模型、语音、图片理解全部跑在本机，数据零出设备 |
| 目标平台 | Android 8.0（API 26）及以上，主力 ABI `arm64-v8a` |
| 包名 | `com.pocketcpm.app` |
| 交付形态 | 自签名 APK 侧载（不上商店，不需要算法备案/软著） |
| 核心模型 | MiniCPM-V 4.7（OpenBMB，Apache-2.0），双档：1B 保底 / 35B-A3B 旗舰 |
| 制作方式 | 独立自研 App，仅复用开源推理运行时（llama.cpp / sherpa-onnx），不基于官方示例 App 改造 |

### 1.1 要解决的问题

云端 AI 助手在三个场景下不好用：地铁/飞机/电梯里没网；发票、体检单、身份证这类图片不敢往外传；以及"只想问一句话，却要等半秒网络往返"。端侧多模态模型到了 MiniCPM-V 4.7 这一代，1B 版本 Q4 量化后连视觉模块不到 2GB，已经能在主流手机上跑到可用速度——这是这个项目成立的前提。

### 1.2 目标（第一版必须做到）

1. **真离线**：装好模型后拔掉网线、开飞行模式，文字问答、看图问答、语音输入、朗读全部正常。
2. **双档自适应**：App 首次启动探测设备内存，自动推荐 1B 或 35B-A3B，低端机不崩、旗舰机不浪费。
3. **看得懂图**：拍照/相册传图提问，能读小票、截图、路牌、表格。
4. **能听会说**：按住说话转文字（离线 ASR），回答可朗读（离线 TTS）。
5. **不烫手**：连续对话 10 分钟不出现热降频导致的"卡死感"，有明确的性能预算并实测达标。

### 1.3 非目标（这一版明确不做）

- ❌ 不做联网、不做账号、不做云同步、不做订阅。
- ❌ 不做 Agent / 工具调用 / 联网检索。
- ❌ 不做图片生成、视频生成。
- ❌ 不做 35B-A3B 的"满血"下载（21GB 桌面版），只做官方手机版分片。
- ❌ 不做 iOS / 鸿蒙（架构上留口，但不实现）。
- ❌ 不做视觉 grounding / 画框定位（原因见 §7.3，模型侧有未修复的已知缺陷）。

## 2. 模型事实基线

这一节是全篇的地基。网上关于"3GB 跑 35B"的说法混着好几个不同口径的数字，先把真实数字摊开，后面的排期和体积预算全部从这里推导。

### 2.1 MiniCPM-V 4.7 两个版本

| 维度 | 1B 版 | 35B-A3B 版 |
|---|---|---|
| 架构 | Dense（约 1.01B 参数，官方成绩表标注 1.3B） | 稀疏 MoE，总参 35.2B，每 token 激活约 3B，256 专家取 8 |
| 语言主干 | Qwen3.5 系 | Qwen3.5/3.6 系，3:1 线性注意力与全注意力交替 |
| 视觉塔 | SigLIP2，ViT 内早期压缩（LLaVA-UHD v4 技术） | 同左 |
| 视觉 token 压缩 | 4× / 16× 可选 | 4× / 16× 可选 |
| 权重体积 | Q4_K_M ≈ **641–672 MB** | 桌面 GGUF Q4_K_M ≈ 21.2 GB；手机版 **单文件** `mix_q3gud_im.gguf` **14.44 GB** + 视觉模块 1.04 GB ≈ **15.5 GB**（实测确认，不是"40 个专家分片"） |
| 视觉模块 | mmproj f16 16× ≈ **1.11 GB**；4× ≈ 0.85 GB | 同左（按压缩档选一个） |
| 首次下载合计 | **约 1.8 GB** | **约 16.6 GB** |
| 运行内存 | 官方硬件表建议 RAM ≥ **4 GB** | 官方硬件表建议 RAM ≥ **12 GB** |
| 常驻内存 | 桌面实测进程约 2.5 GB | 官方口径约 **3 GB**（这是激活专家的常驻值，不是全量） |
| 端侧速度 | 官方未公布手机数据。**本机实测（Ryzen 7 7735H / 8 线程 / Q4_K_M / b11669）：解码 29–35 tok/s，纯文本首字 0.1–0.2 s，视觉编码 36 tok/s** | 官方：iPhone 17 Pro Max 约 3GB 内存下 13+ tok/s，iPad Pro M4 17+ tok/s。**本机实测（无 LES，15.2GB 机器）：解码 5.4–8.6 tok/s，内存工作集 10.2 GB，小票问答 50 s** |
| 端侧加速技术 | 不需要（dense 模型） | **LES 前瞻专家调度** + 细粒度逐层量化 + **DSpark** 投机采样草稿头。**实测：upstream llama.cpp 就能加载运行**（语言模型是 `qwen35moe` 架构），LES 只影响速度不影响可用性 |
| License | Apache-2.0（可商用） | Apache-2.0 |

> 关键结论：**1B 版是 dense 模型，上游 llama.cpp 原生就能跑，不需要 LES。** 35B-A3B 想要可用速度则必须走 OpenBMB 的 `llama.cpp-omni` 分支。这直接决定了我们分两条运行时路线，而不是一条。

### 2.2 基准成绩（官方口径，Instruct 模式）

1B 版：MMBench 81.20 / OCRBench 86.10 / OCRBench v2 49.46 —— 相比上一代 4.6 全面提升，但 MathVista、OmniDocBench 略低于 4.6。

35B-A3B 版：MMBench 91.72 / OCRBench 91.20 / OmniDocBench v1.6 94.24 / MathVista 88.00 / Video-MME 76.40 / ScreenSpot 86.99。

**这些全是官方自测，尚无同口径第三方复核。** 计划书里引用它们只作为"选型依据"，不作为验收标准——验收一律用我们自己构造的真实任务集（§10.1）。

### 2.3 已知缺陷（必须在设计阶段规避）

| 问题 | 影响 | 我们的对策 |
|---|---|---|
| 上游 llama.cpp 对 MiniCPM-V 4.7 的 image marker token 分配了错误的 RoPE 位置（应按瓦片角坐标，实际按纯文本编号），修复 PR 于 10-14 提交、截至 10-20 未合并 | 问"图里某物在哪里"返回的坐标**系统性偏低** | 第一版**不做画框/坐标定位功能**；纯描述、OCR、问答不受影响。后续若需 grounding，改用带修复的 fork |
| 模型默认开启 thinking（先输出 think 段再作答） | 输出额度被思考吃掉，用户看到空白；体验很差 | Chat 场景**默认关闭 thinking**（llama-server 侧 `--reasoning off`，JNI 侧通过 chat template kwargs 传 `enable_thinking=false`；并保留一个"深思模式"开关给推理题） |
| 小模型算术不稳：本机实测同一张柱状图两次求和给出 402 和 442（正确 402），**即使把算式写出来也会错**；小票总额两次给出 212.86 / 197.86 | 账单、报表类任务数字可能错 | UI 上对含金额/数量的回答一律加"请人工复核"提示；不做静默信任；验收集里必须有负面用例 |
| LES 只存在于 `llama.cpp-omni` 分支，非上游主线 | 分支可能跟不动上游、可能停更 | **实测 upstream 也能跑 35B**（只是慢）。所以 35B 可以先用 upstream 上线，LES 作为独立提速项后加，不阻塞主链路 |
| 手机版 35B 是单个 **14.44 GB** 权重文件 + 1.04 GB 视觉模块 | 下载 15.5GB 易中断、易失败；且 14.44GB 在 8GB 机上根本放不下 | 自研下载器：断点续传 + SHA256 校验 + 支持从 PC 用 adb/文件选择器导入；**12GB 以下机型直接不提供这一档** |
| **4.7 的视觉投影器需要新版 llama.cpp**：实测 `unknown projector type: minicpmv4_7`，语言部分正常、视觉部分加载即失败 | 拿旧运行时开工会直接卡死 | **M0 第一件事就是确认运行时能加载 4.7 的 mmproj**；不行则换 `llama.cpp-omni` 或改按 4.6 做视觉 |
| **上游 llama.cpp 到 b11669（最新 nightly）都没注册 `minicpmv4_7`**，只到 `minicpmv4_6` | 装上模型直接加载失败，视觉完全不可用 | 用 `tools/patch-mmproj.py` 把 mmproj 里的投影器标识原地改一位（两串等长，不动偏移），实测等价。**打包时做成可选开关**，上游修好后撤掉 |
| 视觉编码吞吐只有 36 tok/s（纯文本预填 127–219 tok/s） | 图片首字 6.5–14 s，是体验最大杀手 | 默认图片长边 **1024**（实测 11.7 s / 381 token）。降到 640 只省 5 s，但小票小字全读错。要压到 5 s 内必须上 GPU 后端 |

## 3. 产品形态

### 3.1 界面骨架（三个页面 + 一个抽屉）

1. **对话页（主）**：消息流 + 输入栏。输入栏左侧是"+"（相册/拍照/文件），右侧是麦克风长按说话、发送按钮。回答流式逐字出现，可中断。
2. **模型页**：模型卡片列表（1B / 35B-A3B），显示体积、是否已下载、当前档位、设备适配结论（"你的设备 8GB 内存，推荐 1B"）。
3. **设置页**：思考模式开关、上下文长度、温度、语音语速/音色、深色模式、数据导出与清空、"断网自检"。
4. **会话抽屉**：历史会话列表，可重命名/删除/置顶。

### 3.2 关键交互

- **首启引导**：探测内存与存储 → 给出推荐档位 → 引导下载/导入模型 → 三项自检（文字、图片、语音各跑一次）。
- **图片提问**：选图后自动压缩到长边 1024（可在设置里调到 1600 保清晰），显示"将在本机处理，不上传"角标。
- **语音**：长按说话时实时显示识别中的文本（SenseVoice 非流式，用 VAD 分段 + 500ms 节流重跑模拟流式），松手即发送。
- **生成中**：显示 tok/s 与已生成 token 数（给极客用户看，可关）；有"停止"按钮；长回答自动折叠 think 段。

## 4. 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 语言 / UI | Kotlin + Jetpack Compose (Material 3) | 原生性能可控，Compose 做流式消息列表最省事 |
| 最低 API | minSdk 26 / targetSdk 35 | API 26 覆盖绝大多数在用机型；35 适配分区存储与前台服务新规 |
| 推理运行时（1B） | 上游 **llama.cpp**（NDK 交叉编译，C++ 静态库 + 自写 JNI） | dense 模型上游即够；社区活跃、跟进快 |
| 推理运行时（35B） | **llama.cpp-omni**（OpenBMB fork，带 LES/DSpark） | 唯一能在手机上把 MoE 跑顺的分支 |
| 多模态预处理 | 自己实现：图像解码 → 缩放 → RGB → 与 llama.cpp `libmtmd` 对齐的 patch 切分 | 避免引入 Python 侧依赖，全部 native |
| 语音 ASR | **sherpa-onnx** + SenseVoice-Small int8（约 226–240 MB） | 中文/英文/中英混说、自带标点与数字规范化、非流式但足够快（S10 真机 RTF 0.06） |
| 语音 VAD | sherpa-onnx 内置 Silero VAD（约 0.6–2 MB） | 断句准、极省资源，用来做"说完自动停" |
| 语音 TTS | sherpa-onnx VITS 中文模型（约 60–120 MB，具体型号在 M4 定型） | 完全离线、无需系统语音包；比系统 TTS 可控 |
| 持久化 | Room（会话/消息）+ DataStore（设置） | 常规组合 |
| 下载 | OkHttp + HTTP Range 断点续传 + SHA-256 校验 | 16.6GB 场景必须有 |
| 后台 | 前台 Service（`dataSync` + 常驻通知）承载推理，避免切后台被杀 | 生成 30 秒的回答不该因切走而中断 |
| 构建 | Gradle KTS + CMake（externalNativeBuild）+ NDK r27 | 一次 CMake 编出 `libllamacpm.so` |

### 4.1 明确不选的东西

- **不选 ONNX Runtime 跑 MiniCPM-V**：视觉 token 压缩路径与 3D RoPE 需要改图，收益不成正比。
- **不选 MediaPipe LLM Inference**：官方支持矩阵不含 MiniCPM-V 4.7。
- **不选 Flutter/React Native**：JNI 边界 + 大内存模型 + 长流式输出，跨端框架的胶水成本高于收益。
- **不引入 Python**：全部 native，装机即用。

## 5. 系统架构

### 5.1 分层

```
┌──────────────────────────────────────────────────────┐
│  UI 层（Compose）                                     │
│  ChatScreen / ModelScreen / SettingsScreen / Drawer   │
├──────────────────────────────────────────────────────┤
│  ViewModel 层（StateFlow）                            │
│  ChatVM / ModelVM / VoiceVM / SettingsVM              │
├──────────────────────────────────────────────────────┤
│  领域层（纯 Kotlin，无 Android 依赖）                  │
│  ChatRepository  ConversationRepo  PromptBuilder      │
│  TokenBudget      DeviceProfile     ModelCatalog      │
├──────────────────────────────────────────────────────┤
│  引擎适配层（接口 + 两个实现）                         │
│  LlmEngine (interface)                                │
│   ├── LlamaCppEngine   (dense, 1B)                    │
│   └── OmniEngine       (MoE + LES, 35B-A3B)           │
│  AsrEngine / TtsEngine / VadEngine  (sherpa-onnx)     │
├──────────────────────────────────────────────────────┤
│  JNI 层（C++17）                                      │
│  jni_llm.cpp  jni_mtmd.cpp  jni_asr.cpp  jni_tts.cpp │
├──────────────────────────────────────────────────────┤
│  原生库                                               │
│  libllama / libggml / libmtmd (静态) → libllamacpm.so │
│  libsherpa-onnx-jni.so + libonnxruntime.so            │
└──────────────────────────────────────────────────────┘
```

**核心设计原则：`LlmEngine` 是唯一对外接口。** 上层（ChatRepository / UI）完全不感知用的是 1B 还是 35B、走上游还是 omni。这样 M0 的可行性验证结果、M6 的 omni 接入、以及未来换 Qwen3-VL 或 Gemma，都只换实现类。

```kotlin
interface LlmEngine {
    suspend fun load(model: ModelSpec, cfg: EngineConfig): LoadResult
    fun generate(req: GenerateRequest): Flow<GenEvent>   // Token / Done / Error
    suspend fun abort()
    fun unload()
    val stats: StateFlow<EngineStats>                    // tok/s、内存、上下文占用
}
```

流式用 `Flow<GenEvent>` 而不是回调：Compose 侧 `collectAsState` 一行搞定，且 `abort()` 天然可取消。

### 5.2 分层 Gradle 模块

```
:app                    组装、导航、DI
:core:design            主题、色板、通用组件（消息气泡、Markdown 渲染）
:core:data              Room、DataStore、Repository
:core:device            设备探测（内存/存储/CPU/ABI/热状态）
:feature:chat           对话页
:feature:model          模型管理页
:feature:voice          语音（ASR/TTS/VAD 的生命周期与状态机）
:engine:api             LlmEngine 接口、GenEvent、ModelSpec
:engine:llamacpp        上游 llama.cpp JNI 封装
:engine:omni            omni 分支 JNI 封装
:native:llama           CMake 工程 + C++ 源码 + 预编译脚本
```

多模块的价值在于：`engine:omni` 单独编译、单独可能坏掉，不会拖垮主 App。

### 5.3 一次问答的完整链路

```
用户输入（文字 / 图片 / 语音）
   ↓
[语音] VAD 检测到静音 700ms → SenseVoice 转文本 → 回填输入框
   ↓
[图片] 解码 → 长边压到 1024 → RGB888 → 交给 libmtmd 切 patch
   ↓
TokenBudget 计算：系统提示 + 历史轮次 + 图片 token 数 ≤ 可用上下文
   ↓（超了就按轮次从旧到新裁掉，保留 system 和最后一轮图片）
PromptBuilder 按 MiniCPM-V 4.7 的 chat template 拼 prompt
   ↓（注入 enable_thinking=false）
LlmEngine.generate() → JNI → llama_decode 循环
   ↓
每生成 1~4 个 token 回调一次 → Flow → Room 落库（批量，每 200ms 或 32 token）
   ↓
Compose 逐字上屏；用户点"停止"→ abort → 已完成部分正常入库
   ↓
[TTS] 若开启朗读：按句号切句，边生成边合成，播放队列不阻塞生成
```

**边生成边朗读**这个细节很重要——如果等整段答完再合成，用户要干等十几秒。

## 6. 模型策略：按机型自适应

### 6.1 分级规则

启动时读 `ActivityManager.MemoryInfo.totalMem` + 可用存储 + `Build.SOC_MODEL`（API 31+）：

| 内存档位 | 可选模型 | 上下文 | 默认视觉压缩 | mmproj | 说明 |
|---|---|---|---|---|---|
| < 6 GB | 1B Q4_K_M | 2048 | 16× | f16 16× | 保守，防 OOM |
| 6–8 GB | 1B Q4_K_M | 4096 | 16× | f16 16× | **主力档** |
| 8–12 GB | 1B Q5_K_M 或 Q6_K | 4096 | 4× 或 16× | 按需 | 质量优先 |
| ≥ 12 GB 且存储 ≥ 20 GB | 1B + **35B-A3B（可选）** | 1B:4096 / 35B:2048 | 35B 用 q3gud-im 配套 | — | 旗舰机尝鲜 |
| ≥ 16 GB | 同 12GB 档，上下文可提到 4096 | | | | |

**图片长边默认 1024。** 实测（4.7 1B，PC 8 核）：640→228 token/6.1 s，但小票商品名**全部读错**；1024→381 token/10.9 s，商品名 6 项对 5 项。**1024 是"能读"的底线，不能为了省 5 秒降到 640**。真机嫌慢优先上 GPU 后端，而不是降分辨率。

**不自动下载 35B。** 16.6GB 必须用户明确点"我要下"才启动，而且要二次确认（提示流量、存储、发热）。

### 6.2 双模型共存

两个模型都下好时，对话页顶部给一个切换器（`1B 快速` / `35B 深度`）。**不允许同时加载**——加载 35B 前必须 `unload()` 1B 并等内存回收，否则 8GB 机必 OOM。切换时保留会话，重新 build prompt 即可。

### 6.3 模型文件布局

```
filesDir/models/
  minicpm-v-4.7-1b/
    MiniCPM-V-4_7-1B-Q4_K_M.gguf      641 MB
    mmproj-model-f16.gguf             1.11 GB
    manifest.json                     {sha256, size, quant, downloadedAt}
  minicpm-v-4.7-35b-a3b-les/
    MiniCPM-V-4_7-35B-A3B-q3gud-im.gguf
    experts/shard-00..39.gguf         共约 16.6 GB
    mmproj-model-f16.gguf
    dspark-MiniCPM-V-4_7-35B-A3B-F16.gguf   0.74 GB（投机采样草稿头，可选）
    manifest.json
  voice/
    sensevoice-small-int8/model.int8.onnx   ~230 MB
    silero_vad.onnx                          ~1 MB
    vits-zh/model.onnx                       ~80 MB
```

`manifest.json` 是真理之源：校验、断点、删除都靠它。

## 7. 关键技术难点与对策

### 7.1 NDK 交叉编译 llama.cpp

CMake 必须关掉几个开关（都是硬约束，不是可选项）：

| 选项 | 值 | 原因 |
|---|---|---|
| `GGML_NATIVE` | OFF | 交叉编译时宿主机 CPU ≠ 目标 CPU，native 探测会得出错误指令集 |
| `GGML_OPENMP` | OFF | NDK 侧 CMake 无法正常定位安装 OpenMP |
| `GGML_LLAMAFILE` | OFF | llamafile 后端不支持 Android |
| `LLAMA_OPENSSL` | OFF | OpenSSL 不在 NDK 稳定原生 API 集合里，且默认为 ON |

ABI 只出 `arm64-v8a`（`armeabi-v7a` 跑不动模型，纯属浪费体积），`ANDROID_PLATFORM=android-28`。

**指令集策略**：不加全局 `-march`，让 ggml 运行时探测 CPU 特性自动选内核——否则在老机型上直接 SIGILL。

**GPU 加速**：ggml 有 OpenCL 后端（Adreno/Mali 部分可用）。第一版**不启用**，理由是多模态编码器在 GPU 上的兼容性还没稳，收益不确定、调试成本高。

> ⚠️ 实测后修正：视觉编码是这个 App 唯一的延迟瓶颈（22–24 tok/s，见 `docs/02-技术验证报告.md`）。**如果要求看图首字压到 5 秒以内，GPU 后端就从「M7 可选实验」升级为「M3 必做」**——1024 长边在 CPU 上就要 11 s，靠降分辨率只会把准确率赔进去。

### 7.2 多模态数据通路

llama.cpp 侧走 `libmtmd`（`mtmd_*` 系列 API）。我们要在 JNI 里把 Bitmap 转成一维 float 数组传下去，关键点：

- 图像缩放在 Kotlin 侧用 `BitmapFactory` + `inSampleSize` 做两级降采样（先按 2 的幂快速降，再精确缩），避免大图直接进 native 爆内存。
- 传下去不要传 Bitmap 对象指针（GC 会动），传 `ByteBuffer`（direct）+ 宽高。
- **16× 压缩**：速度快、token 少，适合"图里是什么"；**4× 压缩**：细节多，适合读小票/表格。两个 mmproj 加起来 1.96GB，第一版**只装 16×**，4× 作为可选下载（用户手动开"高清视觉模式"）。

### 7.3 已知缺陷规避（写进代码约束）

- **不做 grounding**：不实现"框出图中目标"功能，也不在 prompt 里索取坐标。若用户问"在哪"，引导为文字描述。
- **thinking 默认关**：JNI 侧构造 chat template 时传 `enable_thinking=false`；UI 提供"深思"开关（数学/推理题建议开）。这是 M1 阶段必须先验证的点——若 llama.cpp 侧无法通过 template kwargs 关掉，则退化为 prompt 层面加"直接回答，不要输出思考过程"+ 输出后正则剥离 `think` 段。
- **数字不静默信任**：含金额/数量/日期的回答，气泡下方加"AI 生成，数字请核对"小字。

### 7.4 内存治理（最容易翻车的地方）

1. `unload()` 必须走完整路径：`llama_free` → `mtmd_free` → 释放 direct buffer → `System.gc()` 提示 → 等 300ms 再加载新模型。Android 的 native 堆不会自动回收，漏一步就是 OOM。
2. `onTrimMemory(TRIM_MEMORY_RUNNING_LOW)` 时主动 `unload()`（仅在无生成任务时）。
3. 上下文按 token 预算硬裁，而不是"设了 4096 就一直塞到 4096"——图片 token 一次能吃 2000+。
4. 生成过程的 KV cache 会持续增长，长回答要监控 `ctx_used`，超过阈值提前收尾。

### 7.5 热与续航

- 默认线程数 = 大核数（`Runtime.availableProcessors().coerceAtMost(4)`，多数手机给 4 最平衡；8 线程会因能效核争抢反而变慢）。
- 监听 `PowerManager.OnThermalStatusChangedListener`（API 29+）：`SEVERE` 以上时自动把 max tokens 砍半并提示用户。
- 屏幕熄灭时暂停生成（前台 Service 保活但不烧电）。

### 7.6 语音链路的坑

- SenseVoice 是**非流式**：不能边说话边出字。方案是 VAD 每检测到一个断句点就送一段（通常 1–3 秒音频）+ UI 上显示"识别中…"，并在 500ms 节流内重跑当前累积段做"伪流式"预览。真机 RTF 0.06，重跑几次完全扛得住。
- 唤醒词不做（VAD + 长按足够，唤醒词要常驻监听，费电且误触）。
- TTS 按句切分后串行合成，播放用 `AudioTrack`；与 ASR 互斥（录音时必须停播，否则自激）。

## 8. 里程碑与排期

单人全职口径，共 **10 周**。每周一个可验证产出，不允许"做完了但看不到"。

| # | 里程碑 | 工期 | 交付物 | 通过标准（Gate） |
|---|---|---|---|---|
| **M0** | 可行性验证 | 1 周 | PC 侧 NDK 编出 `llama-cli`，推到真机跑 1B 模型 | 真机跑通文字问答 + 一次看图问答；记录 tok/s、内存峰值、首字延迟。**若 1B 在目标机 < 8 tok/s，整份计划需要重新评估** |
| **M1** | 骨架 + 推理打通 | 1.5 周 | Compose 空壳 + `engine:llamacpp` + JNI 流式输出 | 输入文字 → 逐字上屏；停止按钮有效；thinking 能关掉 |
| **M2** | 会话与持久化 | 1 周 | Room、多会话、抽屉、Markdown/代码块渲染、重新生成 | 杀进程重进，历史与滚动位置都在 |
| **M3** | 多模态 | 1.5 周 | 图片选择/拍照、压缩、mmproj 加载、图片 token 预算 | 10 张小票/截图测试集，OCR 关键字段（金额、日期）准确率 ≥ 70% |
| **M4** | 语音 | 1.5 周 | VAD + SenseVoice + VITS 全链路 | 5 米内正常语速说话，识别可用；朗读自然度主观 ≥ 及格 |
| **M5** | 模型管理 | 1 周 | 下载器（续传/校验/导入/删除）、设备分级推荐、双模型切换 | 断网中途重连能续；从 PC 导入 16.6GB 成功 |
| **M6** | 35B-A3B 通道 | **3–4 天**（原 1.5 周） | 单文件加载 + 模型切换 + 体积/内存门槛判断 | 12GB 机上跑起来 ≥ 5 tok/s；1B↔35B 切换不 OOM。**实测 upstream 就能跑，不必先趟 omni 编译** |
| **M7** | 打磨与出包 | 1 周 | 引导流程、自检、深色模式、热控、签名 APK、README | 飞行模式下全功能自检 100% 通过 |

### 8.1 关键路径与缓冲

关键路径：**M0 → M1 → M3 → M6**。M1 的 JNI 流式一旦打通，M2/M4/M5 可以并行推进（如果有多人）；单人则顺序做。

风险缓冲放在 M6（omni 分支最不可控）和 M3（多模态预处理最需要调）。若 M6 卡住，**可以整块砍掉不影响交付**——1B 单档的 App 依然是完整可用的产品，这是排期上刻意设计的"可裁剪点"。

### 8.2 建议的第一个动作

不要先写 UI。**先花两天把 M0 做透**：把 1B 模型丢到真机上，用 Termux 或直接编个最小 `llama-cli`，实测三个数——tok/s、内存峰值、首字延迟。这三个数决定了后面所有参数（上下文多长、能不能开 4× 压缩、语音能不能和模型同时驻留）。计划书里所有性能数字都是估算，M0 之后要用实测值回填本文档。

## 10. 验收标准

### 10.1 功能验收（真实任务集，不吹不黑）

建一套 40 条的自测集，出厂前跑一遍：

| 类别 | 条数 | 通过标准 |
|---|---|---|
| 中文闲聊/常识 | 10 | 回答切题，无重复循环、无乱码 |
| 长文本理解（500 字后提问） | 5 | 能准确引用文中信息 |
| 图片描述 | 5 | 主要物体/场景描述正确 |
| 截图/小票 OCR | 10 | 关键字段（金额/日期/编号）≥ 70% 正确 |
| 中英混说语音输入 | 5 | 转写可读，意图能懂 |
| 朗读 | 5 | 能听清，无破音、无截断 |
| **算术负面**（心算，不给算式） | 5 | 必须能观察到错，且界面对数字有复核提示 |
| **金额负面**（小票问"一共多少"） | 5 | 商品金额与应付金额必须都能被问到，答错要有提示 |
| **时间推理负面**（多约束路牌） | 5 | 已知会错，用于验证兜底文案是否触发 |

### 10.2 性能预算（8GB 中端机 / 1B Q4_K_M / 4 线程基准机）

> 下表已按 `docs/02-技术验证报告.md` 的 PC 实测结果修正过一轮。原稿「看图首字 ≤ 4 s」在 CPU 上不可能达成，已放宽到 10 s。

| 指标 | 目标 | 不可接受 |
|---|---|---|
| 模型加载时间 | ≤ 5 s | > 15 s |
| 纯文本首字延迟 | ≤ 1.5 s（实测 0.2 s，有余量） | > 4 s |
| 看图首字延迟（1024 长边） | ≤ 12 s（PC 实测 10.9 s） | > 18 s |
| 解码速度 | ≥ 12 tok/s（实测 PC 29–35） | < 8 tok/s |
| 内存峰值 | ≤ 3.2 GB | OOM |
| 连续对话 10 分钟 | 无降频卡顿 | 明显卡顿 |
| 冷启动到可输入 | ≤ 2.5 s | > 5 s |

### 10.3 体积预算

| 组成 | 体积 |
|---|---|
| APK（含 sherpa-onnx so + VAD） | 60–80 MB |
| 1B 模型全套 | ~1.8 GB |
| 语音全套（ASR + VAD + TTS） | ~320 MB |
| **首次装机合计** | **约 2.2 GB** |
| 加装 35B-A3B | +16.6 GB |
| 加装 4× 高清视觉 | +0.85 GB |

### 10.4 隐私验收（硬性）

- 飞行模式 + 拔出 SIM，全功能可用。
- 提供一个"零网络权限"构建变体：不声明 `INTERNET`，模型只能从 PC 导入。**这是给"我完全不信"的用户准备的版本，也是最好的自证。**
- 应用内不集成任何分析 SDK、不集成崩溃上报（自用项目不需要，且会让"离线"承诺变味）。

## 14. 一句话总结

这个项目的技术风险不在"能不能跑"，M0 一周就能给出答案；真正的工程量在**内存治理、双档自适应、语音链路和模型分发**这四件事上。架构上已经把最不可控的部分（35B-A3B 的 omni 分支）做成可裁剪模块，所以最坏情况是交付一个"1B 完整版"，而不是一个"什么都做了一半"的东西。
