## 一、结论

1. **4.7 的视觉能跑。** 需要绕过上游一个登记缺失（见 §五），绕过之后文字、看图、读表全部可用，10 条用例全过。
2. **文本很快，视觉很慢。** 纯文本首字 **0.1–0.2 s**、解码 **29–35 tok/s**；看图首字 **6.5–13.8 s**，因为视觉编码吞吐只有 **36 tok/s** 左右。首字延迟的大头全在图片上。
3. **1B 的能力边界很清晰。** 场景描述、图表读数、格式约束都行；算术会错、小票金额会选错行、多约束时间推理会反。这些必须在产品层兜底，不能靠"再调调参数"。

## 二、文本用例

| 用例 | 输出 | 判定 | 首字 | 解码 |
|---|---|---|---|---|
| 解释 MoE（三句话，讲给高中生） | 三句、结构清楚（专家混合→小组合作→神经元类比） | ✅ | 0.2 s | 32.6 tok/s |
| 3−2+5 的算术，只给答案和算式 | 「4 / +2 -1 +5 = 8」 | ❌ **答错**（应 6） | 0.2 s | 34.5 tok/s |
| 按价格排序，只输出列表 | 「320元、18元、9.5元」 | ⚠️ 顺序对，但没按"列表"格式 | 0.2 s | 34.7 tok/s |
| 不知道就明说（问今天深圳天气） | 先说「我不知道」，后面又猜了一段 | ⚠️ 半对 | 0.1 s | 29.2 tok/s |

**算术这条要重点记**：同一个问题，4.6 版答对（6），4.7 版答错。1B 的数学能力不是"稳定弱"，是"随机弱"——产品上任何涉及数字的地方都不能静默信任。

## 三、视觉用例

| 用例 | 图 | 图像 token | 首字 | 解码 | 判定 |
|---|---|---|---|---|---|
| 描述照片（灯塔/黄昏） | 768×768 | 232 | 6.5 s | 29.9 | ✅ 很准，说了光影、云层、情绪 |
| 细节提问（最亮处/右下角） | 768×768 | 229 | 6.6 s | 31.4 | ✅ 右侧暖光、右下礁石浪花 |
| OCR（截图逐行读） | 860×297 | 287 | 7.6 s | 32.9 | ⚠️ 主体对，长串字符有错 |
| 小票抽取 | 992×1408 | 522 | 21.8 s* | 32.1 | ⚠️ 商品全对，总额选错行 |
| 柱状图读数＋求和 | 1140×750 | 496 | 13.8 s | 33.2 | ⚠️ 读数全对，求和两次不同（402 / 442） |
| 多约束时间推理（路牌） | 960×930 | 398 | 9.7 s | 32.9 | ❌ 逻辑反了 |

\* 该次命中了 prompt 缓存，冷启按 522 token 折算约 14 s。

### 值得逐条看的四个点

**描述类：明显强于 4.6。** 4.6 说"黄昏、宁静略带神秘"；4.7 说"云层厚重的阴沉预示可能要下雨，而夕阳余晖添了一丝温柔，整体孤独苍凉又略带敬畏"。同一张图，信息量和文笔差一档。

**图表：读数稳，求和不稳。** 五根柱子的数值每次都读对（128/96/74/61/43），但求和结果不稳：

| 轮次 | 输出 | 正确吗 |
|---|---|---|
| 第 1 次 | `128 + 96 + 74 + 61 + 43 = 402` | ✅ |
| 第 2 次 | `128 + 96 + 74 + 61 + 43 = 442` | ❌ |

**算式写出来了也照样错。** 这条否掉了我原本"只要有算式就可信"的猜测——1B 的算术是全程不可靠，跟有没有写出过程无关。产品上任何数字结论都必须配复核提示，没有例外。

**小票：商品 6 项全对，总额错了。**
问"一共花了多少钱"，答 212.86（商品金额），正确是 197.86（应付金额）。
同一张票在不同轮次里有时答 197.86、有时答 212.86 —— **是采样不稳定地"猜字段"，不是稳定算错**。比稳定错更危险，因为你不测就发现不了。

**路牌：方向反了。**
答"11:00-14:00 禁止停车，所以你需要在 14:00 之前开走"。
正确理解是：11:20 到达时**已经不能停**，得等到 14:00 之后。模型把"禁停时段"读成了"在此之前离开的截止时间"。这类多约束时间推理是 1B 的明确短板。

## 四、分辨率－延迟－准确率三角

同一张 992×1408 的小票，只改长边：

| 长边 | 图像 token | 视觉编码 | 总耗时 | 小票商品名识别 |
|---|---|---|---|---|
| 640 | 228 | 6.1 s | 6.9 s | ❌ 全崩：「有机牛奶粉 25ml」「现烤全虫叶 40g」「藤椒面筋」「鲜冷翅五花肉 50g」「云南小胡咖啡豆 20g」「厨房张市」 |
| 1024 | 381 | 10.9 s | 11.7 s | ✅ 6 项中 5 项完全正确，只有「冷鲜黑猪五花肉」漏了个「鲜」 |

**结论跟直觉相反：为了省 5 秒把图片压到 640，小票就废了。**

- 视觉编码吞吐恒定在 **36 tok/s 上下**，与图像内容无关，只跟 token 数走。所以首字延迟 ≈ 图像 token ÷ 36。
- 512→640 的 token 数几乎不变（204→228，切片阶梯效应），省不到时间还丢细节。
- 640→1024 的 token 翻倍，但**这是"能读"和"读不了"的分界线**。

**所以默认长边定 1024**，不是 640。真机上如果嫌慢，先上 GPU 后端，别先降分辨率。

## 五、4.7 视觉的运行时坑（本次最大的发现）

拿现成运行时直接跑，第一步就死：

```
clip_init: load_hparams: unknown projector type: minicpmv4_7
```

排查过程：

| 方案 | 结果 |
|---|---|
| LM Studio 自带 llama.cpp（commit 448147d） | ❌ 不认 `minicpmv4_7` |
| 官方 llama.cpp **最新 nightly b11669** | ❌ `mtmd.dll` 只注册到 `clip_graph_minicpmv4_6` |
| 官方 v0.7.0 正式版 | 只有源码，没有 Windows 二进制 |
| 自己编 `llama.cpp-omni` | 可行但重（42 MB 源码 + 编译），且下载被限速 |
| **改写 mmproj 里的投影器标识** | ✅ **成了** |

**怎么绕的**：4.7 和 4.6 的视觉塔是同一套结构（SigLIP2 + 16× 压缩），只是 GGUF 元数据里写了个新名字。而 `"minicpmv4_7"` 和 `"minicpmv4_6"` **长度完全一样（12 字节）**，所以可以原地替换，不改变任何偏移：

```bash
python testbed/tools/patch-mmproj.py models/mmproj-model-f16.gguf
# → models/mmproj-4.7-patched.gguf（1.06 GB，长度不变，只有 1 处字节不同）
```

验证：改写后图片描述、小票 OCR、图表读数、柱状图求和全部正常，说明两条视觉路径确实等价。

**这个手段的代价与风险**（必须写进产品说明）：

- 官方没有承诺二者等价，我们是靠实测确认的。**上线前要用扩展测试集复验**，不能只靠这 10 条。
- 视频理解路径没有充分验证——4.7 的视频分支可能引入 3D RoPE 差异，这一版先不承诺视频。
- 上游一旦合并 `minicpmv4_7`（或改用 omni 分支），这个补丁就该撤掉。**打包脚本里要做成可选开关**，不要硬编码。

> 另外：`llama.cpp-omni` 仍然是 35B-A3B 的必需品（LES 专家调度只在那个分支）。所以 4.7 视觉虽然绕过去了，omni 这条线不能丢。

## 九、35B-A3B 试跑（2026-10-25 下午补测）

### 先纠正一个之前的错判

我在 §五 里写过"35B-A3B 必须用 omni 分支"。**这是错的。**

拿 `mix_q3gud_im.gguf` 的文件头解析出来，`general.architecture = qwen35moe`——它的语言模型是 Qwen3.5-MoE 架构，
而 upstream llama.cpp b11669 的符号表里就有 `llama_model_qwen35moe`。**LES 是提速手段，不是加载前提。**

顺带纠一个传言：手机版不是"40 个专家分片"，就是一个 14.44 GB 的单文件 `mix_q3gud_im.gguf` + 1.04 GB mmproj。
所谓"3GB 内存"是激活专家的常驻值，不是下载体积。

### 测试条件

| 项 | 值 |
|---|---|
| 权重 | `MiniCPM-V-4_7-35B-A3B-mix_q3gud_im.gguf` 14.44 GB |
| 视觉模块 | 官方 `mmproj-model-f16`，同样打了一字节补丁 |
| 运行时 | llama.cpp b11669，**无 LES、无 DSpark** |
| 参数 | `-c 2048 -t 8 -ngl 0 --no-warmup` |
| 机器 | 15.2 GB 内存（模型 14.44 GB，几乎贴顶） |

### 结果

**加载**：14 秒起来（mmap）。启动时有告警 `failed to fit params to free device memory ... abort`，但服务正常。

**内存**：工作集 **10.2 GB**、私有 3.4 GB，系统可用内存只剩 **0.4 GB**。全程靠缺页把专家权重从 SSD 换进来——这也是速度上不去的原因。

**速度**：

| 场景 | 预填 | 解码 | 单次总耗时 |
|---|---|---|---|
| 纯文本（16 tok） | 2.4 s | 5.35 tok/s | 4.3 s |
| 算术（短问） | — | 5.70 tok/s | 7.4 s |
| 小票（502 图像 token） | 29.0 s | 8.10 tok/s | **49.6 s** |
| 路牌（~400 图像 token） | 24.0 s | 8.60 tok/s | **80.1 s** |

模型热起来之后解码反而快（5.3 → 8.6），因为常用专家已经进了页缓存。

### 质量：1B 栽的三个坑，它全填了

| 用例 | 1B 结果 | 35B 结果 |
|---|---|---|
| 3−2+5 算术 | ❌ 答「4 / = 8」 | ✅ **「6 个 / 3 - 2 + 5 = 6」** |
| 小票总额 | ❌ 反复在 212.86 / 197.86 之间摇摆 | ✅ **「197.86 元」并主动拆解**：「商品总金额 212.86，会员折扣 −15.00，最终应付 197.86」 |
| 路牌时间推理 | ❌ 把禁停时段读成「离场截止时间」 | ✅ 明确说「11:20 到达时处于禁停时段内，**不能停车**」，并算出「14:00 后停入 → 最晚 16:00」 |

小票那条尤其说明问题：1B 是"找到了两个数字但选错行"，35B 是"把三行金额的关系讲明白"。**这不是运气，是理解层次的差别。**

路牌那题仍有一处绕：它把「最晚几点必须开走」答成 14:00，逻辑上 11:20 就不该停，表述含混。但核心判断（禁停时段内不能停）是对的，而 1B 彻底反了。

### 结论：35B 的价值和代价

| | 1B | 35B-A3B |
|---|---|---|
| 下载体积 | 1.7 GB | **15.5 GB** |
| 这台机器上的解码 | 29–35 tok/s | **5.4–8.6 tok/s** |
| 内存占用 | ~3.1 GB | **10.2 GB**（还会把系统榨干） |
| 小票问答耗时 | ~17 s | **~50 s** |
| 算术 / 字段选择 / 时间推理 | ❌ 都错 | ✅ 都基本对了 |

**值不值，取决于用户拿它干什么。**
- 问"这是什么""帮我读一下这段" → 1B 完全够，快 5 倍、省 12 GB。
- 读账单、核对金额、算数、看路牌 → 35B 是唯一可靠的，1B 会稳定给错答案。

这也印证了计划书里的双档设计：**不是"贵的更好"，是"错的场景必须用贵的那档"**。

### 对计划书的修正

1. **§2.3 / §8.1「35B 必须 omni 分支」** → 改为"upstream 即可运行，omni 只影响速度"。M6 从"高风险不可控"降级为"可控但费体积"。
2. **§2.3 删掉"40 个专家分片"的说法**，实际是单文件 14.44 GB。
3. **M6 工期可以从 1.5 周压到 3–4 天**——不用趟 omni 编译。
4. **LES 的价值需要单独验证**：真机上没 LES 会掉到多少，决定要不要为它接 omni。这台机器上没 LES 是 5.4–8.6 tok/s，官方带 LES 的 iPhone 数据是 13+ tok/s，量级对得上。

### 没验证的

- **LES 本身**：没编 omni，不知道能提升多少。
- **DSpark 投机采样**：没下草稿头（0.74 GB）。
- **4× 高清视觉**：35B 只用了 16× 的 mmproj。
- **更长上下文**：只跑 2048，实际手机端需求可能到 4096。
- **热稳定性**：这台机器内存贴顶，跑久了会 swap；真机是另一种压力模型。

### 结论与待办

1. **文本侧完全达标**：33.9 tok/s 聊天体验流畅，与 PC 持平，路线不用改。
2. **视觉编码是硬瓶颈**：CPU 编 1 图约 7 分钟，完全不可用。下一步按优先级试：

4. 未测：8 线程对比、Vulkan GPU、server 常驻 + UI 原型连真机、长上下文与热稳定性。

## 十一、GPU 加速尝试（2026-10-26 傍晚，K60 Pro）

视觉编码慢是 CPU 的硬限制，试着把计算搬到 Adreno 740。

### Vulkan：编译成功，运行崩溃（不可用）

- 交叉编译通过（需要 MinGW 宿主工具链编译着色器生成器 + SPIRV-Headers + Vulkan-Headers，且 `ANDROID_PLATFORM` 必须 28+，否则 `std::aligned_alloc` 缺失）。
- 设备能识别：`Vulkan0: Adreno (TM) 740 (11446 MiB)`。
- 但一加载模型就 abort：`pre-allocated tensor (cache_k_l3) in a buffer (Vulkan0) that cannot run the operation (NONE)`；带视觉时是 `v.vit_merger.ds_ffn_up.weight`。
- 试过 `-fa on/off`、`--no-kv-offload`、`-ngl 0 --mmproj-offload`，全部同样失败。判定：b11669 的 ggml-vulkan 在 Adreno 740 上算子覆盖不全，暂不可用。

### OpenCL：可用，视觉编码提速 7 倍（当前方案）

- 必须 `GGML_OPENCL=ON`（自带 `GGML_OPENCL_USE_ADRENO_KERNELS`），链接期用一个空桩 `libOpenCL.so`（运行时由设备的 `/system/vendor/lib64/libOpenCL.so` 提供符号，该库在 `public.libraries.txt` 白名单里，App 可加载），并加 `-Wl,--unresolved-symbols=ignore-all`（NDK 默认 `--no-undefined`）。
- 设备识别：`GPUOpenCL: QUALCOMM Adreno(TM) (5595 MiB)`。
- **注意**：`-ngl 99` 时上下文创建失败（单次分配要 1.65GB，Adreno 上限更低），需 `-c 2048 -ub 128`。

实测（同一张 992×1408 小票，问 6 件商品+总价）：

| 配置 | 总耗时 | 图像 prompt | 生成 | 质量 |
|---|---|---|---|---|
| CPU（4 线程） | 7 分 23 秒 | 1.2 t/s | 18.2 t/s | 6/6 全对 |
| OpenCL 全 GPU（`-ngl 99 -c 2048 -ub 128`） | 1 分 16 秒 | 11.8 t/s | 5.0 t/s | 商品金额正确 |
| **OpenCL 混合（`-ngl 0 --mmproj-offload`）** | **1 分 03 秒** | 11.1 t/s | 17.2 t/s | **6/6 + 总价 212.86 全对** |
| CPU + 512 长边图 | 1 分 30 秒 | 1.3 t/s | 18.9 t/s | 小字全错（幻觉商品名） |

纯文本：CPU 33.9 tok/s vs OpenCL 5.2 tok/s → **LLM 必须留在 CPU**，只把视觉编码器放 GPU。

`--image-max-tokens` 无效（不减少编码器计算量），真正影响耗时的是喂进去的图片像素尺寸。

### 当前 App 配置

`-c 4096 -t 4 -ngl 0 --mmproj-offload`，minSdk 由 26 提到 28（OpenCL 构建用 API 28 编译）。

## 附：本次踩到的环境坑（给下次省时间）

| 坑 | 症状 | 解法 |
|---|---|---|
| GitHub 直连 | 超时 | 走 `gh-proxy.com` / `ghproxy.net` |
| 代理单连接限速 | 4–10 KB/s | **Range 分片并发**（`tools/fetch2.sh`），16 路约 400 KB/s |
| 分片脚本 append 重试 | 文件越下越大、gzip 校验失败 | 每片独立文件 + 校验 206 + 精确长度，绝不 append |
| pip 装包 | 能连上索引，但解析出 0 个候选 | 不可用。需要时用 curl 下 wheel + `pip install --no-index` |
| 本地 HTTP 请求 | 被系统代理劫持 | curl 加 `--noproxy "*"`；Python 用 `ProxyHandler({})` |
| PowerShell 画图 | `Add-Type` / `Assembly.Load` 被拦 | 用无头 Chrome 截 HTML（`--headless --screenshot`） |
